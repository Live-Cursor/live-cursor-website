Getting Started

Plugin Overview

Live Cursor is an advanced, offline-first, zero-cloud collaborative sync engine designed specifically for private Obsidian vaults. By leveraging Yjs conflict-free replicated data types (CRDTs) and a local background daemon, it lets you edit vaults simultaneously with team members without exporting your data to third-party databases.

Why Zero-Cloud?

Standard real-time collaborative editors require a cloud registry to sequence and resolve keystrokes. Live Cursor routes sync traffic directly between your connected clients and your own local sync daemon, which persists Yjs room state to plain files on your own disk — maintaining absolute privacy for your intellectual property.

Key Capabilities

Keystroke-level Merging

Never deal with Git line conflicts or overwriting other authors again. CRDTs merge changes deterministically at the character level.

Metadata & Settings Sync

Dynamically propagates workspace configurations, pane positions, and custom styles across connected devices.

Offline Resilience

Work fully offline; changes buffer locally and cleanly merge upon reconnecting to the team node.

End-to-End Private

No data ever leaves your own network. Use wss:// for encrypted transport over your local LAN or VPN tunnel.

Getting Started

Manual Installation

Live Cursor is not yet in the Obsidian Community Plugins catalog, so for now install it manually (or via the BRAT plugin). These are the lightweight packaging steps.

1. Grab Compiled Releases

Download the latest compiled release bundle from GitHub. The plugin directory requires two fundamental assets:

  • main.js — The compiled execution logic.
  • manifest.json — Metadata containing configuration permissions.

2. Place Assets in Vault

Move these assets to your target vault's hidden plugin directory:

bash 
# Create the target directory inside your Obsidian vault plugins folder
mkdir -p .obsidian/plugins/live-cursor

# Copy your downloaded release files into the directory
cp main.js manifest.json .obsidian/plugins/live-cursor/

3. Reload Plugins

Navigate to Obsidian Settings > Community Plugins, disable and re-enable Live Cursor (or restart Obsidian), then configure it from its own settings tab.

BRAT Alternative

Power users can install BRAT (Beta Reviewers Auto-update Tool) and add Live-Cursor/Live-Cursor as a beta plugin. Obsidian then handles downloads and updates automatically.

Plugin Settings Reference

Setting Default Description
Server Connection URL ws://localhost:4444 Base WebSocket endpoint of the sync daemon
Room Name default-live-cursor-room Namespace for the session; all devices must match exactly
Server Password default-pass Shared auth token; the server rejects the wrong password. Change it before connecting anything beyond localhost.
Collaborator Nickname Me Display name shown on peer cursors

Changes Apply Instantly

Changing the room name, server URL, or password reconnects all open files automatically — no restart or manual reconnect needed.

Getting Started

Vault Quickstart

To synchronize vaults, a background sync database must be running. We provide an embedded sync server inside the plugin settings or a detached Docker container for remote execution.

Bootstrap local server in 15 seconds

  1. Open Obsidian Settings > Live Cursor.
  2. Under Local Sync Server, click Start Local Server to boot the daemon on port 4444 in the background.
  3. Under Connection & Room, pick a Room Name and a strong Server Password. Every device must use the exact same values.
  4. Under Your Profile, set your display name and cursor color.
  5. You are now ready to collaborate! Share your local network address (e.g., ws://192.168.1.100:4444) with teammates — they enter it in their Server Connection URL.

Always Change the Default Password

The server ships with the default password default-pass. Anyone who knows your server's address and the default password can read and write your vault files. Set a strong AUTH_TOKEN before connecting anything outside your own machine.

For advanced custom configurations, use our interactive Guided Setup Wizard to instantly compile Docker Compose or environment manifests.

Connecting Remote Teammates

Once your daemon is running, teammates connect by entering your server's WebSocket URL into their plugin settings. There are three network topology options:

01
Local Network (LAN)

Fastest option. All devices must be on the same Wi-Fi or ethernet segment. Use your machine's LAN IP address.

ws://192.168.x.x:4444
02
Tailscale VPN

Best for remote teams. Tailscale creates a secure encrypted mesh between devices anywhere on the internet.

ws://100.x.x.x:4444
03
Self-Hosted Server

Deploy on a VPS, NAS, or home server using Docker. Expose via reverse proxy with HTTPS/WSS.

wss://sync.yourdomain.com

All devices must also share the exact same Room Name and Server Password — the plugin builds the per-file room paths automatically.

Architecture

Daemon Infrastructure

The Live Cursor daemon is a Node.js process with a WebSocket listener for relaying operations and an HTTP API for vault file sync. It persists Yjs room state to plain binary files on disk — no SQLite, no external databases.

Docker Container Deployment

If you prefer a headless server running on a NAS, server, or cloud node, deploy the precompiled Alpine Docker container from GitHub Container Registry.

docker 
# Deploy the Docker container on port 4444
docker run -d \
  --name live-cursor-server \
  -p 4444:4444 \
  -v live-cursor-data:/app/data \
  -e PORT=4444 \
  -e DB_DIR=/app/data \
  -e AUTH_TOKEN=your-strong-password \
  ghcr.io/live-cursor/sync-server:latest

Docker Compose (Recommended)

For persistent, auto-restarting deployments, use the official Compose manifest:

yaml 
version: '3.8'
services:
  live-cursor:
    image: ghcr.io/live-cursor/sync-server:latest
    container_name: live-cursor-server
    restart: unless-stopped
    ports:
      - "4444:4444"
    volumes:
      - live-cursor-data:/app/data
    environment:
      - PORT=4444
      - DB_DIR=/app/data
      - AUTH_TOKEN=your-strong-password

volumes:
  live-cursor-data:

Environment Parameters

The daemon respects standard environment variables for easy tailoring:

Variable Default Description
PORT 4444 WebSocket & HTTP listener port
DB_DIR ./data Directory for Yjs room state (rooms/) and synced vault config (config/)
AUTH_TOKEN default-pass Shared password required on every request. Change it for any deployment beyond localhost.

Security Notice

Never expose port 4444 directly to the public internet without placing it behind a reverse proxy (e.g., Caddy or Nginx) with TLS termination. Use Tailscale for zero-config encrypted remote access instead.

Architecture

Network Protocol

Communication between Obsidian clients and the sync daemon occurs over WebSockets using the standard y-websocket protocol, alongside a small HTTP API for vault-wide file sync. Every endpoint requires the shared AUTH_TOKEN.

Authentication

All requests must present the server's AUTH_TOKEN:

  • WebSocket: the token is passed as a ?token= query parameter. Connections with the wrong token are closed immediately.
  • HTTP API: the token is sent as an Authorization: Bearer <token> header.

Without a valid token the server answers 401 Unauthorized — the vault is no longer readable by anyone on the network.

Rooms & Persistence

Each open note maps to a room with the form <room-name>/<file-path>. Rooms are persisted to disk as binary state files named <sha1(workspace)>-<sha1(room)>.bin under data/rooms/, so long paths can never collide. Vault-wide config sync lives under data/config/<room-name>/.

HTTP API

Endpoint Method Description
/api/manifest GET List synced files for the workspace
/api/upload POST Upload a file; merges markdown into Yjs room state without destroying CRDT history
/api/download GET Fetch a file from the workspace
/api/delete DELETE Delete a file and its room state
/api/room-state GET/POST Fetch or merge binary CRDT state for a room
/api/reconstruct-db POST Purge room state for the current workspace only

Connection Lifecycle

Phase Direction Description
Handshake Client → Daemon WebSocket upgrade with ?token= auth param; wrong token rejected
SyncStep1 Client → Daemon Client sends its current Yjs state vector
SyncStep2 Daemon → Client Daemon replies with all missing document updates
Live Sync Bidirectional Real-time delta keystrokes and awareness states
Reconnect Client Auto-reconnects on mobile wake, network resume, window focus, or settings change

Disk Persistence

The daemon persists Yjs room state to data/rooms/ with a 500 ms debounce after every update, so documents survive restarts. Deletions made while offline are queued by the plugin and retried until the server confirms — deleted files never resurrect.

Architecture

CRDT Merge Logic

Conflict-free Replicated Data Types (CRDTs) form the mathematical foundation of Live Cursor's concurrent editing capability.

Why git diffs fail real-time edit resolution

Git utilizes line-based three-way merges. If two authors edit different portions of the exact same line at the same time, Git is unable to resolve order, prompting a merge conflict.

Yjs manages text as a doubly linked list of character chunks. Each chunk contains:

  • ID: A unique key containing the author's client code and an incremental sequence number.
  • Origin Left / Origin Right: Pointers targeting the adjacent characters at the time the keystroke was pressed.

This guarantees that even if 10 people type concurrently inside the same paragraph, all keystrokes are merged in exactly the same deterministic order across every single peer.

Awareness Protocol

Alongside document sync, Live Cursor propagates real-time awareness state — lightweight JSON objects broadcasting each peer's cursor position, selection range, and collaborator name. Awareness updates are never persisted to disk; they are ephemeral and discarded when a client disconnects.

typescript 
// Live Cursor sets collaborator awareness on each file sync
provider.awareness.setLocalStateField('user', {
  name: settings.nickname || settings.username || 'Collaborator',
  color: settings.cursorColor || '#6366f1',
  colorLight: (settings.cursorColor || '#6366f1') + '33'
});

Performance Characteristic

Yjs CRDT updates are binary-encoded using lib0 encoding, keeping delta sizes extremely small — typically under 50 bytes per keystroke even in complex collaborative sessions.

Networking

Tailscale Setup

Tailscale is the recommended networking solution for sharing your Live Cursor daemon with remote teammates. It creates an encrypted peer-to-peer mesh network (using WireGuard® under the hood) where every device gets a stable private IP address — no port forwarding, no firewall rules, no dynamic DNS needed.

Zero-Config Encrypted Networking

Tailscale handles NAT traversal, encryption, and authentication automatically. Once installed, every device on your tailnet can reach your Live Cursor daemon as if it were on the same local network.

Step 1 — Install Tailscale on the Host Machine

The host machine is the device running the Live Cursor daemon (local background process or Docker container). Install Tailscale on this machine first.

bash 
# Install Tailscale on Debian/Ubuntu
curl -fsSL https://tailscale.com/install.sh | sh

# Authenticate and connect to your tailnet
sudo tailscale up

# Confirm your Tailscale IP (100.x.x.x range)
tailscale ip -4
bash 
# Install via Homebrew
brew install tailscale

# Start and authenticate
sudo tailscaled &
tailscale up

# Or download the App from the Mac App Store (recommended)
# https://apps.apple.com/app/tailscale/id1475387142
powershell 
# Download installer from https://tailscale.com/download/windows
# Or install via winget:
winget install tailscale.tailscale

# After installation, sign in from the system tray icon
# Confirm your Tailscale IP
tailscale ip -4
yaml 
# docker-compose.yml — Live Cursor + Tailscale sidecar
version: '3.8'
services:
  tailscale:
    image: tailscale/tailscale:latest
    hostname: live-cursor-node
    environment:
      - TS_AUTHKEY=${TS_AUTHKEY}
      - TS_STATE_DIR=/var/lib/tailscale
    volumes:
      - tailscale-state:/var/lib/tailscale
      - /dev/net/tun:/dev/net/tun
    cap_add:
      - NET_ADMIN
    restart: unless-stopped

  live-cursor:
    image: ghcr.io/live-cursor/sync-server:latest
    network_mode: "service:tailscale"
    volumes:
      - ./data:/app/data
    environment:
      - PORT=4444
      - DB_DIR=/app/data
      - AUTH_TOKEN=your-strong-password
    restart: unless-stopped
    depends_on:
      - tailscale

volumes:
  tailscale-state:

Step 2 — Install Tailscale on Teammate Devices

Each collaborator installs Tailscale on their device and joins your tailnet (Tailscale network). You can invite them via email from the Tailscale admin console.

  • Download from tailscale.com/download for all platforms including iOS and Android.
  • Once connected, every device sees others via stable 100.x.x.x IPs — these never change.
  • For Obsidian mobile users, Tailscale runs in the background and maintains the VPN tunnel automatically.

Step 3 — Configure Live Cursor to Use Tailscale IP

Once Tailscale is running on all devices, update the Live Cursor server URL to point to the host machine's Tailscale IP instead of its local LAN address:

settings 
# In Obsidian → Settings → Live Cursor → Server URL
# Replace with the host machine's Tailscale IP:

ws://100.x.x.x:4444

# Example with a specific IP:
ws://100.64.0.12:4444

# To find the host's Tailscale IP, run on the host machine:
tailscale ip -4

Step 4 — Using MagicDNS (Optional but Recommended)

Tailscale's MagicDNS feature assigns human-readable hostnames to every device on your tailnet, so you never need to remember IP addresses.

settings 
# Enable MagicDNS in the Tailscale Admin Console:
# https://login.tailscale.com/admin/dns

# Then use the hostname instead of IP in Live Cursor:
ws://my-desktop.tail12345.ts.net:4444

# Or if you set a custom domain:
ws://live-cursor-node:4444

For organizations, you can restrict which Tailscale devices can reach your Live Cursor daemon using Access Control Lists (ACLs) in the admin panel.

json — tailscale acl 
{
  "acls": [
    {
      "action": "accept",
      "src": ["tag:obsidian-collab"],
      "dst": ["tag:live-cursor-server:4444"]
    }
  ],
  "tagOwners": {
    "tag:obsidian-collab": ["autogroup:member"],
    "tag:live-cursor-server": ["autogroup:admin"]
  }
}

Frequently Asked Questions

How is my vault data protected?

Two layers. First, every HTTP and WebSocket request must present the shared AUTH_TOKEN — the server rejects connections with the wrong password, so your vault is not readable by anyone on the network. Second, traffic stays inside your own network; when using Tailscale it is additionally encrypted with WireGuard-grade encryption at the network layer, and wss:// can be used behind a reverse proxy for TLS.

What happens if I edit offline?

Changes buffer locally and merge cleanly when the server becomes reachable again, using CRDT merge semantics — no manual conflict resolution required. File deletions made while offline are queued and retried until the server confirms, so deleted notes never resurrect.

Does this increase the size of my Markdown files?

No. The operational histories are recorded in separate binary room-state files on the server. Your Markdown vault notes remain fully standard, clean, and free of any bloating tracking markers.

Can I use Live Cursor on mobile (iOS / Android)?

Yes! The plugin is fully supported on Obsidian mobile. Live Cursor automatically reconnects whenever the app becomes visible or the network comes back online. For remote access on mobile, pair it with the Tailscale mobile app for reliable encrypted connectivity from anywhere.

How many users can collaborate simultaneously?

There is no hard user limit built into Live Cursor. Practical limits depend on the host machine's resources. The Node daemon uses async I/O, comfortably handling 10–20 concurrent editors on modest hardware. The Docker deployment on a NAS or small VPS handles even more.

Do I need Tailscale, or can I use my own VPN?

Tailscale is recommended for its zero-config simplicity, but any VPN solution that provides IP-level routing between devices works. This includes WireGuard, OpenVPN, ZeroTier, or a traditional site-to-site VPN. As long as the WebSocket URL is reachable, Live Cursor will connect.
